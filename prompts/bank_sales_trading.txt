# [SPIDER2 BANK & SALES DOMAIN RULES] - STRICT OVERRIDE

1. LITERAL TRANSLATION RULE (CRITICAL):
If the prompt explicitly says "subtract all withdrawal amounts", you MUST ONLY subtract `txn_type = 'withdrawal'`. 
- DO NOT subtract 'purchase' or any other types. 
- Correct formula: `SUM(CASE WHEN txn_type = 'deposit' THEN txn_amount WHEN txn_type = 'withdrawal' THEN -txn_amount ELSE 0 END)`

2. "ALL CUSTOMERS" DENOMINATOR RULE (FATAL):
When calculating an average "across all customers", you MUST NOT use the `AVG()` function.
- You MUST manually calculate it as: `SUM(metric) * 1.0 / (SELECT COUNT(DISTINCT customer_id) FROM customer_transactions)`
- The denominator must be the total unique customers in the ENTIRE table, without any date filters.

3. ABSOLUTE DIFFERENCE RULE (FATAL):
If the prompt asks for the "difference" between two values, you MUST wrap the final subtraction in the `ABS()` function (e.g., `ABS(val1 - val2)`).

4. RANKING TIE-BREAKER RULE (FATAL):
When finding the highest or lowest month based on a count, you MUST NOT use `RANK()` or `DENSE_RANK()`.
- You MUST use `ROW_NUMBER() OVER (ORDER BY count_metric DESC, month_col ASC)` to ensure only exactly one month is selected even if there is a tie.

5. MISSING MONTHS PADDING RULE (FATAL):
If evaluating all months in a year (e.g., 2020), you MUST NOT just `GROUP BY` the transaction data, because months with zero transactions will disappear.
- You MUST create a calendar CTE with all 12 months (e.g., '2020-01' to '2020-12').
- `LEFT JOIN` the aggregated transaction stats to this calendar and use `COALESCE(val, 0)` to fill missing months.

6. NO GREATEST FUNCTION:
SQLite does NOT support the `GREATEST()` function. Use a `CASE` statement.

7. PREVIOUS METRICS & DATE FILTERS (FATAL):
- When finding a "previous day's volume", use a correlated subquery.
- FATAL DATE FILTER RULE: If a date window is specified, apply it ONLY in the VERY LAST `WHERE` clause.
- Output the formatted date (`YYYY-MM-DD`).

8. OUTPUT COMPLETENESS RULE (CRITICAL):
If the prompt asks to "determine which [item] has the highest/lowest [metric A]" and "compute [metric B] and provide the difference", your final SELECT statement MUST output ALL of the following as separate columns:
1. The identifier for the highest item (e.g., highest month)
2. The [metric A] for the highest item (e.g., highest positive count)
3. The [metric B] for the highest item (e.g., highest avg balance)
4. The identifier for the lowest item (e.g., lowest month)
5. The [metric A] for the lowest item (e.g., lowest positive count)
6. The [metric B] for the lowest item (e.g., lowest avg balance)
7. The final calculated difference
NEVER just output the identifiers and the difference. You MUST include all intermediate metrics in the final SELECT list.

9. MASSIVE TABLE OPTIMIZATION (TIMEOUT PREVENTION):
- NEVER apply string/date functions like `DATE(col)` or `STRFTIME()` to columns inside `JOIN ON` conditions or `WHERE` clauses. It disables database indexes and causes fatal timeouts.
- If data profiling shows two date columns share the exact same format (e.g., both end with ' 00:00:00'), `JOIN` them directly using equality (`A.txn_date = B.whsle_date`).
- Use index-friendly range filters instead of functions (e.g., `txn_date >= '2020-01-01 00:00:00' AND txn_date < '2024-01-01 00:00:00'` instead of `STRFTIME('%Y', txn_date) BETWEEN '2020' AND '2023'`).

10. DIMENSION AVERAGE FAN-OUT RULE (CRITICAL):
- When calculating averages (`AVG`) or finding max/min of dimension attributes (like wholesale price or loss rate) grouped by a higher level (like category), you MUST NOT aggregate directly after joining with the massive sales transaction table. Sales volume will cause Fan-out and weight the averages incorrectly.
- You MUST use a CTE with `SELECT DISTINCT` to isolate the unique attribute values first (e.g., `SELECT DISTINCT year, category_name, item_code, whsle_date, whsle_price FROM ...`) and THEN apply `AVG()`, `MAX()`, `MIN()` on that specific CTE.

11. RETAIL TOTAL LOSS FORMULA (CRITICAL):
- When calculating the "total loss" value based on a loss rate percentage, you MUST calculate it based on the *purchased* quantity, not just the sold quantity.
- Use this exact mathematical formula: `SUM(whsle_price * (qty_sold / (1.0 - loss_rate_percent / 100.0) - qty_sold))`

12. VEGETABLE SALES FILTER RULE:
- Whenever you aggregate or analyze transaction data from the `veg_txn_df` table, you MUST strictly apply the filter `"sale/return" = 'sale'` to exclude returned items, unless the prompt explicitly asks for returns.
