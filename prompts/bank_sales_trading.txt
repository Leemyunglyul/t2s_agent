# [CRITICAL SQL TEMPLATES]
When facing the following specific problems, you MUST use these exact SQL structures. Do not invent your own logic.

**Template 1: Zero-Filled Cumulative Monthly Balance (Crucial for Rule 9 & 12)**
If the prompt asks for "monthly balances", "closing balances", or "monthly changes" for EACH customer, including months with NO activity, use this EXACT structure:
WITH RECURSIVE DateRange AS (
    SELECT DATE(MIN(txn_date), 'start of month') as current_month, DATE(MAX(txn_date), 'start of month') as end_month FROM base_table
    UNION ALL
    SELECT DATE(current_month, '+1 month'), end_month FROM DateRange WHERE current_month < end_month
),
AllCustomerMonths AS (
    SELECT DISTINCT t.customer_id, d.current_month FROM base_table t CROSS JOIN DateRange d
),
MonthlyActivity AS (
    SELECT customer_id, DATE(txn_date, 'start of month') as txn_month,
           SUM(CASE WHEN txn_type = 'deposit' THEN amount ELSE -amount END) as net_change
    FROM base_table GROUP BY customer_id, txn_month
)
SELECT a.customer_id, a.current_month, COALESCE(m.net_change, 0) as monthly_change,
       SUM(COALESCE(m.net_change, 0)) OVER (PARTITION BY a.customer_id ORDER BY a.current_month) as closing_balance
FROM AllCustomerMonths a
LEFT JOIN MonthlyActivity m ON a.customer_id = m.customer_id AND a.current_month = m.txn_month;

**Template 3: Bulletproof Volume/String Parsing**
When parsing volume columns that contain 'K', 'M', '-', or raw numbers:
CASE 
    WHEN col LIKE '%K%' THEN CAST(REPLACE(col, 'K', '') AS REAL) * 1000 
    WHEN col LIKE '%M%' THEN CAST(REPLACE(col, 'M', '') AS REAL) * 1000000

# [DOMAIN-SPECIFIC SQL RULES]

**Cross-Domain Join Prevention (CRITICAL)**: This database contains multiple independent datasets merged together (e.g., Bank, Sales, Trading, Crypto). NEVER join tables across different business domains just because they have similar column names (e.g., linking crypto `member_id` with bank `customer_id`). If you need "region" for crypto transactions, look for a specific crypto dimension table (like `members`), DO NOT use `customer_regions` or `customer_nodes` from the banking domain. Always verify table relationships before joining.

***--- Data Prep & Dates ---***
1. **Strict Table/Column Adherence (CRITICAL)**: Use EXACTLY the tables mentioned in the prompt (e.g., "bitcoin_prices"). Do not hallucinate or substitute tables.
2. **Date Normalization & Format Trap (CRITICAL)**: 
- NEVER use raw date/timestamp columns directly in `JOIN` conditions ONLY IF they have different formats. 
⚠️ `bitcoin_transactions.txn_date` and `bitcoin_prices.market_date` are `DD-MM-YYYY` (MUST convert using `SUBSTR` before joining). 
⚠️ **CRITICAL TIMEOUT WARNING**: `customer_transactions.txn_date`, `veg_txn_df.txn_date`, and `veg_whsle_df.whsle_date` are ALREADY perfectly formatted as `YYYY-MM-DD`. **YOU MUST NEVER USE `DATE()` OR `STRFTIME()` ON THEM IN JOIN CONDITIONS.** Join them directly as raw strings (e.g., `ON t.txn_date = w.whsle_date`) to utilize indexes. Using `DATE()` on these massive tables during a join WILL crash the database.
3. **The `BETWEEN` Inclusivity Trap**: SQL `BETWEEN` is INCLUSIVE. "4 weeks leading up to June 15" means `BETWEEN DATE('...-06-15', '-28 days') AND DATE('...-06-15', '-1 day')`.
4. **Never Early Filter**: NEVER filter out prior years inside your foundational transaction CTEs. Cumulative past balances will be lost. Filter the target year ONLY at the very bottom `SELECT`.
5. **"Most Recent Month" Trap (CRITICAL)**: If a prompt asks for a metric based on a customer's "most recent month", "latest month", or "last transaction", you MUST identify this month using `MAX(date)` from the RAW transaction table for each specific customer (e.g., `SELECT customer_id, DATE(MAX(txn_date), 'start of month') ... FROM customer_transactions GROUP BY customer_id`). DO NOT use the global `MAX(month)` from a zero-filled calendar. Zero-filling pads the tail with inactive months, which will artificially force the customer's "most recent" growth rate or net change to 0% and ruin the final percentage.

***--- Balances & Transactions ---***
1. **Banking Balance Terminology (CRITICAL)**: In financial/banking datasets, terms like "month-end balance" or "closing balance" ALWAYS require a **cumulative running total** (e.g., `SUM(net_change) OVER (PARTITION BY customer_id ORDER BY month)`). Do NOT be fooled if the prompt explicitly says "calculate the balance by adding deposits and subtracting withdrawals during that month" — this phrasing only describes the monthly delta, which MUST still be accumulated to previous balances to find the true account balance.
2. **Transaction Types**: Treat `txn_type = 'purchase'` exactly the same as `withdrawal` (reduces balance). Exception: If explicitly told to "group all deposits and withdrawals", use `WHERE txn_type IN ('deposit', 'withdrawal')` to ignore purchases.
3. **Floor & Negative Replacement**: 
- Running Balance: ONLY apply `MAX(0, balance)` using a Recursive CTE if explicitly asked to "treat negative running balances as zero".
- Final Output: If asked to "replace negative balances with zero" for a total sum, apply it BEFORE summing: `SUM(CASE WHEN user_balance < 0 THEN 0 ELSE user_balance END)`.

***--- Time Series & Window Functions ---***
1. **Continuous Zero-filled Calendar (CRITICAL)**: For Rolling Averages, Month-over-Month `LAG()`, or Grouping by month, you MUST generate a continuous calendar using a Recursive CTE first.
2. **Recursive CTE Calendar Boundary (CRITICAL)**: When generating a calendar using `WITH RECURSIVE`, ALWAYS use strictly less than (`<`) for the boundary condition (e.g., `current_month < '2020-12-01'`), NOT less than or equal (`<=`). Using `<=` will generate an unintended extra period (e.g., January of the next year) and ruin subsequent aggregations and rankings.
3. **Strict Order for Window Functions**: SQL evaluates `WHERE` BEFORE window functions. Compute `LAG()` over the ENTIRE dataset inside a CTE, and apply the `WHERE` filter ONLY in the final `SELECT` query.
4. **Lag Ignore Zeros (Correlated Subquery)**: To fetch the "most recent non-zero value" for a previous day, use a correlated subquery: `(SELECT value FROM calendar c2 WHERE c2.date < c1.date AND c2.value > 0 ORDER BY c2.date DESC LIMIT 1)`. 

***--- Joins & Aggregations ---***
1. **Prevent Join Explosions (Theta Join CRITICAL)**: SQLite WILL crash if you join massive tables using `BETWEEN` on raw rows. You MUST physically aggregate the transactions FIRST (`CREATE TABLE temp_agg AS SELECT ... GROUP BY ...`), and ONLY join this aggregated table to the target.
2. **Dimensional Average Trap (Fan-out)**: DO NOT calculate `AVG()` AFTER joining with a transaction table. Calculate the average inside a CTE independently first, and then join it.
3. **Unpivot via UNION ALL**: When analyzing multiple attribute columns (region, platform, age_band) in the same output format, use: `SELECT 'region' AS attr, region AS val ... UNION ALL SELECT 'platform' ...`

***--- Math & Output Evaluation Strictness ---***
1. **Percentage Change & Division Math (CRITICAL)**: 
- ALWAYS cast to `REAL` or multiply by `100.0` before division to prevent integer truncation.
- ALWAYS handle division by zero using `NULLIF`: `(current - previous) * 100.0 / NULLIF(previous, 0)`
2. **Strict Edge-Case Math Adherence**: If the prompt provides a SPECIFIC mathematical fallback (e.g., "if the previous month is zero, growth rate is current * 100"), you MUST implement EXACTLY that logic using `CASE WHEN previous = 0 THEN current * 100.0 ELSE ... END`. Do not blindly use standard formulas.
3. **Retail Loss Math**: `Wholesale Qty = Sold Qty / (1.0 - loss_rate / 100.0)`. Total Loss = `(Wholesale Qty - Sold Qty) * Wholesale Price`.
4. **Spider2 Strict Output Matching (CRITICAL)**: Spider2 grades by exact column matching. 
- You MUST output EXACTLY the requested columns and NOTHING ELSE. No debugging columns (`customer_id`, `dates`).
- If a question asks for a single "difference" or "percentage", output EXACTLY ONE column and ONE row.
- If asked to round, use `ROUND(value, 2)` on every single numeric output column.
- Standard SQLite DOES NOT support `SQRT()`. If asked for standard deviation, compare using STRICT SQUARES: `col > avg_val AND ((col - avg_val) * (col - avg_val)) > var_val`.
